## 5. V2.2: Human-in-the-Loop Escalation

### What This Milestone Is About

V2.2 adds a human approval gate for medium-confidence decisions. When the agent isn't confident enough to act autonomously but too confident to immediately escalate, it pauses, presents the proposed action to a human, and waits for approval before proceeding.

### Main Goal

Demonstrate that the system supports a hybrid autonomy model: high-confidence decisions execute automatically (V2.1), low-confidence decisions escalate to ServiceNow (V2.1), and medium-confidence decisions pause for human approval before execution.

### Why This Milestone Matters

Enterprise customers cannot deploy fully autonomous remediation without guardrails. Human-in-the-loop provides the safety net that allows organizations to gradually increase autonomy: start with approval for everything, then widen the auto-remediate confidence band as trust builds.

### What Is In Scope (V2.2)

- Human approval gate node in the LangGraph graph.
- Slack interactive messages (buttons: Approve / Reject / Escalate) or Dashboard approval UI *(depends on open question 5.5)*.
- Configurable confidence thresholds for the approval band (e.g., 0.7–0.8).
- Timeout behavior: auto-escalate to ServiceNow if no human responds within N minutes.
- Audit trail showing who approved/rejected and when.

### What Is NOT In Scope (Deferred to V2.3)

- Telco/ORAN use cases.
- Model fine-tuning.
- Complex multi-step approval chains.

### Assumptions and Dependencies

- V2.1 is complete (real ServiceNow, real alerting, real Slack already working).
- If Slack interactive messages are chosen: Slack app manifest must be updated with interactivity URL, and a callback server must be deployed.
- If dashboard UI is chosen: WebSocket or long-polling mechanism needed for real-time approval flow.

## 7. Open Design Decisions

### 7.1 Lightspeed Playbook Persistence Strategy

**Question**: How and when should generated playbooks be persisted to AAP?

**Context**: The current POC bypasses file creation entirely by passing generated YAML through `extra_vars` to a fixed wrapper playbook. This works but means AAP never stores the playbook as a first-class SCM artifact — its audit trail shows the wrapper, not the generated content.

**Options**:
| Option | Pros | Cons |
|--------|------|------|
| A: Commit to AAP project repo (git push) | Full audit trail, replayable, SCM-native | Requires git credentials, slower, merge conflicts possible |
| B: Write to shared volume (PVC) | Simple, fast, accessible by AAP | No version control, cleanup needed, not SCM-native |
| C: Remain ephemeral via extra_vars | Simplest, no persistence infra needed | No audit of actual playbook content, not replayable independently |
| D: Hybrid — extra_vars for execution + git commit for audit | Best of both worlds | Most complex to implement |

**Applies to**: V1.5 (minimal decision), V2.1 (full implementation).

**Decision**: TBD — depends on governance requirements, replayability needs, and operational simplicity.

### 7.2 Lightspeed → Remediate Node Chaining

**Question**: Should the Lightspeed node chain into the Remediate node for execution, or remain a separate terminal path?

**Context**: The proposal is to change the graph so that when Lightspeed generates a playbook for an unknown event type, it feeds into the existing Remediate node for execution (`lightspeed → remediate → notify`) rather than handling execution itself.

**Challenges**:
- Both `lightspeed_node` and `remediate_node` write to the same state fields (`decision`, `remediation_result`), so chaining causes overwrites.
- The remediate step would overwrite Lightspeed's output — losing the `generated_playbook_name`, `generated_template_fields`, and flipping `decision` from "lightspeed" to "remediate", breaking audit lineage.

**Required work if chaining**:
1. Remediate node must support two modes: known-template vs. generated-playbook.
2. State model must preserve full execution history across the chained path (e.g., separate `lightspeed_result` and `remediation_result` fields).
3. New test scenarios for the lightspeed → remediate flow.
4. Audit and notify nodes must handle the combined lineage.

**Applies to**: V2.1.

**Decision**: TBD.

### 7.3 MCP-AAP vs. Direct API Client

**Question**: Do we need MCP-AAP, or should AAP interactions use a simple direct API client?

**Context**: The current agent-service calls AAP tools (`launch_job`, `poll_job_status`, `upsert_job_template`) through LlamaStack's `/v1/tool-runtime/invoke` endpoint, which proxies to the MCP-AAP server. However, all AAP calls are deterministic — the LLM never chooses which AAP tool to call or what parameters to pass. The remediate node hardcodes template names via keyword matching, not LLM-driven selection.

**Arguments for keeping MCP-AAP**:
- Architectural consistency: all 6 external services use the same MCP pattern.
- The quickstart's purpose is to demonstrate the MCP pattern as a reference architecture.
- MCP-AAP already exists and works — removing it is refactoring effort.
- Future possibility: an investigate node or agentic loop where the LLM dynamically queries `list_job_templates` and picks the best one.

**Arguments for replacing with a direct client**:
- Simpler, faster, easier to debug (removes the LlamaStack → MCP-AAP hop).
- Follows the principle of not over-engineering deterministic interactions.
- MCP adds value when the LLM drives tool selection — that's not the case here today.
- Production deployments would likely prefer a direct client for performance.

**Options**:
| Option | Pros | Cons |
|--------|------|------|
| A: Keep MCP-AAP (status quo) | Consistency, demonstrates pattern, already works | Extra hop, over-engineered for deterministic calls |
| B: Replace with direct httpx client | Simpler, faster, honest engineering | Loses MCP narrative, breaks consistency, refactoring effort |
| C: Keep MCP-AAP for quickstart, document direct client as production alternative | Best of both — demo value + honest guidance | Minor doc effort |

**Applies to**: V1.5, V2.1.

**Decision**: TBD.

### 7.4 Alert Source: Grafana vs. Alternatives

**Question**: Is Grafana the right tool for firing alerts into the agent pipeline, or should we use a different mechanism?

**Context**: The V2.1 plan assumes alert rules detect log anomalies and publish to Kafka. However, there are alternative approaches for getting alerts into the system.

**Options**:
| Option | Pros | Cons |
|--------|------|------|
| A: Grafana alert rules → Kafka contact point | Already deployed (LokiStack chart includes Grafana), visual rule editor, standard observability pattern | Extra component to maintain, Grafana alerting can be complex to configure, may be overkill if we only need pattern matching |
| B: Direct Kafka Streams / KStreams processor | No Grafana dependency, lower latency, simpler pipeline (logs → Kafka → filter → agent) | Requires custom code for pattern detection, no UI for rule management |
| C: OpenShift Alertmanager → Kafka | Native to OpenShift, cluster-level alerts already exist, well-understood | Limited to Prometheus-style metrics/alerts, not ideal for log-based detection |
| D: Custom log watcher (ClusterLogForwarder filter + Kafka) | Simplest — filter at the log forwarding layer, only ship error/warning logs to Kafka | Limited pattern matching capability, no complex rule logic |
| E: EDA (Event-Driven Ansible) rulebooks | Aligns with AAP ecosystem, native event processing | Adds another component, may overlap with agent-service's role |

**Key question**: Do we need complex alerting rules (rate thresholds, correlation, silencing) or is simple log-level filtering sufficient for our use cases?

**Applies to**: V2.1.

**Decision**: TBD.
