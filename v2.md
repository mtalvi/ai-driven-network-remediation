## 3. V1.5: Real AAP Execution

### What This Milestone Is About

V1.5 replaces the AAP mock with a real Ansible Automation Platform instance and enables actual playbook execution for both the CrashLoop (known template) and Lightspeed (generated playbook) flows. This is a focused integration milestone that produces a new demo recording.

### Main Goal

Demonstrate that the system executes real Ansible playbooks on a real Automation Platform — both pre-built templates for known failures and AI-generated playbooks for novel failures — fully autonomous, real infrastructure.

### Why This Milestone Matters

V1 proved the agentic workflow with mocks; V1.5 proves the remediation actually works. Audiences can now see real AAP job runs with stdout output, timing, and status in the Controller UI — not just a mock returning success.

### What Is In Scope (V1.5)

- Real AAP instance with real job templates, inventories, and credentials.
- CrashLoop flow executes `restart-nginx` template on real AAP.
- Lightspeed flow generates playbook via ALS and executes it on real AAP via `lightspeed-runner` wrapper template.
- `LIGHTSPEED_SKIP_AAP` flag removed (set to false).
- New demo recording showing real AAP Controller UI with job history.
- Playbook persistence decision: ephemeral via extra_vars is sufficient for V1.5.

### What Is NOT In Scope (Deferred to V2.1+)

- Real ServiceNow PDI (keep mock).
- Alert source wiring (keep manual trigger buttons).
- Human-in-the-loop.
- MCP investigate node.
- Multi-cluster / ACM.
- Telco / ORAN scenarios.
- Model training / evaluation.
- Langfuse.

## 4. V2.1: Real Integrations + Multi-Cluster

## 5. V2.2: Human-in-the-Loop Escalation

### What This Milestone Is About

V2.2 adds a human approval gate for medium-confidence decisions. When the agent isn't confident enough to act autonomously but too confident to immediately escalate, it pauses, presents the proposed action to a human, and waits for approval before proceeding.

### Main Goal

Demonstrate that the system supports a hybrid autonomy model: high-confidence decisions execute automatically (V2.1), low-confidence decisions escalate to ServiceNow (V2.1), and medium-confidence decisions pause for human approval before execution.

### Why This Milestone Matters

Enterprise customers cannot deploy fully autonomous remediation without guardrails. Human-in-the-loop provides the safety net that allows organizations to gradually increase autonomy: start with approval for everything, then widen the auto-remediate confidence band as trust builds.

### What Is In Scope (V2.2)

- Human approval gate node in the LangGraph graph.
- Dashboard approval UI: approval queue with full context, Approve/Reject/Escalate buttons, real-time updates via WebSocket or polling.
- Configurable confidence thresholds for the approval band (e.g., 0.7–0.8).
- Timeout behavior: auto-escalate to ServiceNow if no human responds within N minutes.
- Audit trail showing who approved/rejected and when.

### What Is NOT In Scope (Deferred to V2.3)

- Telco/ORAN use cases.
- Model fine-tuning.
- Complex multi-step approval chains.

### Assumptions and Dependencies

- V2.1 is complete (real ServiceNow, real Slack already working).
- WebSocket or long-polling mechanism needed for real-time approval flow in the dashboard.

### V2.2 Required Work

| # | Task | Description | Priority |
|---|------|-------------|----------|
| 1 | Approval gate graph node | Add a new LangGraph node (or conditional edge) that pauses execution for medium-confidence decisions (configurable threshold band). | High |
| 2 | Approval queue backend | Backend service/endpoint to store pending approvals, expose REST API for approve/reject actions, and signal the paused graph to resume. | High |
| 3 | Dashboard approval UI | Add approval queue component to frontend: pending actions with full context (RCA, evidence, runbook match, proposed action), Approve/Reject/Escalate buttons. WebSocket or polling for real-time updates. | High |
| 4 | Timeout + auto-escalate | If no human responds within configurable timeout, automatically escalate to ServiceNow and notify via Slack. | Medium |
| 5 | Approval audit trail | Record who approved/rejected, when, and the action taken. Include in Kafka audit record and Langfuse trace. | Medium |
| 6 | Configurable threshold band | Make the approval confidence range configurable via env vars (e.g., `APPROVAL_LOW=0.7`, `APPROVAL_HIGH=0.8`). | Low |
| 7 | Demo scenario for approval flow | Create a demo trigger that produces a medium-confidence RCA to exercise the approval path. | Medium |

For medium-confidence decisions, it pauses and presents the proposed action in the dashboard approval queue with full context — RCA, evidence, and runbook match. The engineer reviews and clicks Approve, and the remediation proceeds. If nobody responds within 5 minutes, it auto-escalates to ServiceNow. This gives teams a confidence ramp: start cautious, then widen the auto-remediate band as trust builds."

## 6. V2.3: Telco/ORAN Use Cases + Model Evaluation

V2.3 extends the quickstart into the telecommunications vertical by implementing at least one ORAN-specific failure scenario, ingesting Telco-domain runbooks, and evaluating (optionally fine-tuning) the model on Telco data. This positions the quickstart as a reference architecture for Telco autonomous network operations.

### Main Goal

Demonstrate that the system handles Telco/ORAN-specific failure scenarios with domain-appropriate analysis and remediation, backed by a model evaluated (and optionally fine-tuned) on Telco data.

### Why This Milestone Matters

The Telco/ORAN focus positions this quickstart for the telecommunications vertical — a key Red Hat market. Demonstrating domain-specific intelligence (not just generic Kubernetes remediation) proves the architecture is extensible to specialized industries.

### What Is In Scope (V2.3)

- At least one ORAN-specific failure scenario (e.g., O-RAN RIC xApp crash, fronthaul link degradation, DU resource exhaustion).

- LLM-as-a-Judge evaluation framework using RHOAI 3.4.

## 9. Future Improvements

The following items are deferred beyond the milestones in this document. They represent architectural improvements that are not required for V1.5–V2.3 but should be revisited once the system is production-stable.

### Lightspeed Playbook Persistence

**Current state**: Generated playbooks are passed ephemerally via `extra_vars` to a fixed wrapper playbook (`lightspeed-runner`). AAP executes them but never stores them as first-class SCM artifacts.

**Future improvement**: Persist generated playbooks for full audit trail and replayability. Options include:

| Option | Description |
|--------|-------------|
| Commit to AAP project repo (git push) | Full audit trail, replayable, SCM-native. Requires git credentials and conflict handling. |
| Write to shared volume (PVC) | Simple and fast, but no version control. |
| Hybrid (extra_vars + git commit) | Use extra_vars for execution speed, commit to git for audit. Most complete but most complex. |

**When to revisit**: When governance or compliance requirements demand full traceability of generated playbook content beyond what AAP job stdout provides.

### Lightspeed → Remediate Node Chaining

**Current state**: The Lightspeed node and Remediate node are separate terminal paths in the LangGraph. Lightspeed generates AND executes playbooks independently. This works but duplicates some AAP execution logic.

**Future improvement**: Unify the execution path so Lightspeed only generates the playbook, then hands off to Remediate for execution (`lightspeed → remediate → notify`).

**Challenges that need to be solved**:
- Both nodes write to the same state fields (`decision`, `remediation_result`), so chaining causes overwrites and breaks audit lineage.
- Remediate node would need a dual-mode: known-template vs. generated-playbook.
- State model must preserve full execution history across the chained path (e.g., separate `lightspeed_result` and `remediation_result` fields).
- Audit and notify nodes must handle the combined lineage.

**When to revisit**: When retry/fallback logic is added to the Remediate node (at that point, duplicating it across both paths becomes a real maintenance burden).

### Real Alert Source (Replace Manual Triggers)

**Current state**: Alerts enter the system via manual "Demo Trigger" buttons in the frontend UI. The chatbot-service builds a synthetic event and publishes it to the Kafka `system-alerts` topic. The agent-service consumer is already topic-agnostic and accepts any valid JSON message from `system-alerts` or `noc-alerts`.

**Future improvement**: Replace manual triggers with an automated alert detection mechanism that publishes to Kafka without human intervention. Options include:

| Option | Description |
|--------|-------------|
| Grafana alert rules → Kafka contact point | Visual rule editor, standard observability pattern. Already deployed with LokiStack. Good for complex rules (rate thresholds, correlation, silencing). |
| ClusterLogForwarder filter + Kafka | Simplest — filter at the log forwarding layer, only ship error/warning logs to Kafka. Limited pattern matching. |
| Kafka Streams processor | Custom code filters a raw-logs topic and publishes matches. Lowest latency, no Grafana dependency. |
| EDA (Event-Driven Ansible) rulebooks | Aligns with AAP ecosystem. Supports complex event conditions and throttling. |
| OpenShift Alertmanager → Kafka webhook | Native to OpenShift but limited to Prometheus-style metrics, not log-based detection. |

**Key question to resolve first**: Do we need complex alerting rules (rate thresholds, correlation, silencing) or is simple log-level filtering sufficient? The answer will likely become clearer after V2.3 (ORAN scenarios) when we understand what failure patterns need detection.

**When to revisit**: After V2.3, when Telco/ORAN use cases clarify the detection complexity needed. The manual trigger buttons remain useful for demos regardless.
